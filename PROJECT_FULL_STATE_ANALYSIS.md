## System structure
The repository is a Rust project with both a library target and a binary target, with `src/lib.rs` exporting modules such as `cli_json`, `event_bus`, `execution`, `replay`, `scheduler`, `snapshot`, `workflow`, `lm_control`, `model_manifest`, `embeddings`, and `kernel_types`, while `src/main.rs` is the main CLI entrypoint.[cite:8] The visible source tree also includes `src/execution/runtime.rs`, `src/replay/engine.rs`, `src/replay/capsule.rs`, `src/workflow/compiler.rs`, `src/workflow/contract.rs`, `src/scheduler.rs`, `src/event_bus.rs`, and `src/snapshot.rs`, which together indicate a split between execution, persistence, replay, workflow description, and CLI surfaces.[cite:6]

The test surface is broad and includes architecture boundaries, determinism, scheduler integration, replay capsule behavior, snapshot compatibility, CLI JSON contracts, integrity reporting, semantic artifacts, reuse-policy matrices, and LM control tests.[cite:6] The repository also contains operational scripts and generated verification plans and verdicts under `scripts/`, `docs/`, and `artifacts/`, including `docs/verification_graph.json`, `scripts/run_verification_graph.py`, and multiple `artifacts/verification_plan*.json` and `artifacts/verification_verdict*.json` files.[cite:15]

## Entrypoints and runtime surface
The primary executable entrypoint is `src/main.rs`, which imports JSON reporting helpers, the execution runtime, lease helpers, replay validation, replay capsule building, scheduler functions, snapshot rebuild/restore functions, and workflow compilation types.[cite:8] Inside that file, directly inspected functions include `print_stats`, `table_exists`, `reset_db`, and `integrity_json_report`, showing that the CLI both inspects persistent state and performs control operations over the SQLite-backed kernel state.[cite:8]

The JSON CLI surface is explicitly versioned through `cli-json-v1`, and `src/cli_json.rs` provides shared envelope builders such as `command_report`, `capsule_summary_report`, and `comparison_report`.[cite:10] The current generic command envelope contains top-level `ok`, `schema_version`, `command`, and nested `report`, while capsule summaries additionally expose top-level `task_id`, `execution_id`, `capsule_id`, validity, and graph/event counts.[cite:10]

## Persistence and event model
`src/event_bus.rs` defines `EventBus` over a SQLite connection protected by `Arc<Mutex<Connection>>`, initializes schema from `event_bus/schema.sql`, and exposes append/read paths for both `event_log` and `semantic_artifacts` data.[cite:16] The `append_event` implementation inserts a new row into `generations`, then writes to `event_log` with `system_generation`, `causal_unit_id`, `sequence_in_unit`, `task_id`, `step_id`, `event_type`, canonicalized JSON payload, and `logical_generation`, which is direct evidence that the system uses event persistence as a first-class mechanism for state progression.[cite:16]

The same module also persists semantic artifacts with `task_id`, `step_id`, `source_generation`, `artifact_type`, and canonicalized payload, and offers query functions such as `latest_generation_for_task`, `latest_analysis_seed`, and `list_semantic_artifacts`.[cite:16] This is concrete evidence that the repository already has a semantic artifact layer tied to execution generations rather than ad hoc side files alone.[cite:16]

## Architectural maturity
The current repository is best classified as a **controlled execution system approaching a control-plane architecture**, not yet a fully proven control-plane architecture from the evidence inspected so far.[cite:8][cite:14][cite:16] This classification is supported by the presence of event persistence, replay engine modules, snapshot rebuild/restore, scheduler/worker/execution boundary tests, CLI contract tests, and generated verification graphs/verdicts; however, a repository-wide proof of immutable spec versus observed status separation has not yet been established from the inspected files alone.[cite:8][cite:14][cite:15][cite:16]

The architecture tests are especially strong evidence of intentional subsystem separation: `tests/architecture.rs` asserts that `scheduler` must not import `worker`, `llm`, `embeddings`, `execution`, or `lm_control`; that `worker` must not import scheduler or execution subsystems; that execution code must not import scheduler/worker/lm_control; and that `event_bus` must remain persistence-only.[cite:14] Those tests show that the codebase is enforcing boundaries characteristic of a control-plane style design, even if the full spec/status normalization still needs direct audit across all workflow and runtime types.[cite:14]

## Determinism, replay, and verification evidence
The repository contains explicit replay modules under `src/replay/` and many replay-oriented tests, including `golden_replay_corpus`, replay capsule build/validation/persistence tests, long-chain equivalence tests, seed matrix equivalence tests, and snapshot replay compatibility tests.[cite:6] The attached terminal history also records successful runs for `golden_replaycorpus`, `snapshotversionmatrix`, `schedulerintegration`, `eventorderingfuzz`, and replay capsule tests, alongside generated plan/verdict artifacts with deterministic ordering and environment fingerprint checks.[cite:9]

`tests/determinism.rs` provides at least one explicit deterministic-core assertion that the kernel help surface remains stable even when semantic layers are unavailable.[cite:14] `tests/event_ordering_fuzz.rs` and the attached terminal history show deterministic handling of invalid causal sequences and semantic bias permutations, while the generated verification verdicts mention deterministic order as `topologicalthenprioritythenidversion` and record environment fingerprints for reuse decisions.[cite:9][cite:15]

## Contract surface
The repository has direct contract coverage for CLI JSON, kernel types, workflow plan identity, semantic artifacts, semantic bias observability, LM control behavior, and snapshot compatibility through the visible test files.[cite:6] For the CLI JSON layer specifically, `tests/cli_json_contract.rs` asserts top-level `command`, `schema_version`, and `ok`, while `tests/integrity_json_cli.rs` further requires that `integrity-json` emit `report.snapshot_version == 1`, `report.schema_version == 1`, `report.created_at_present == true`, `report.state_hash_present == true`, `report.state_present == true`, and `report.task_id == "integrity-task"`.[cite:11][cite:12]

The current `src/cli_json.rs` implementation confirms that the generic `command_report` helper does not add top-level `task_id`; it wraps a report under the CLI envelope.[cite:10] Based on the currently inspected tests, that is not yet a confirmed contract violation for `integrity-json`, because the test requires `report.task_id`, not top-level `task_id`.[cite:11][cite:12]

## Observed strengths
The repository already demonstrates several strong control-plane properties: event-backed persistence, generation-aware artifact storage, replay and snapshot modules, deliberate subsystem boundary tests, JSON contract tests, and verification graph artifacts that track execution plans and verdicts.[cite:14][cite:15][cite:16] The terminal history further shows repeated successful verification runs and environment-aware reuse rejection, which is evidence of an engineering workflow that values determinism and reproducibility over ad hoc execution.[cite:9]

## Confirmed risks and open questions
The strongest confirmed risk at this stage is not a proven bug but an **unresolved repository-wide audit gap**: immutable spec versus observed status separation has not yet been demonstrated across workflow, runtime, snapshot, and scheduler types from the files inspected so far.[cite:8][cite:16] The current evidence is also insufficient to claim that a real self-improving execution layer already exists in code; semantic artifact persistence and verification graph tooling exist, but hypothesis generation, instability clustering, and gated improvement proposals have not yet been verified as implemented subsystems.[cite:15][cite:16]

Another concrete caution is historical, not current: the attached terminal history shows earlier concern about whether `integrity-json` needed top-level `task_id`, but the currently inspected test contract only requires `report.task_id`, so that earlier concern must not be treated as an active defect without further test evidence.[cite:9][cite:11][cite:12] There are also generated artifacts modified by prior test runs in `artifacts/`, which means repository status must be interpreted carefully before attributing semantic code changes to current work.[cite:15]

## Current conclusion
From the inspected code and tests, the repository is already beyond a prototype and has many properties of a deterministic kernel/control-plane framework, especially around event logging, replayability, contract checks, and verification orchestration.[cite:8][cite:14][cite:15][cite:16] A strict conclusion that it is already a full normalized control-plane with a real self-improving layer cannot yet be supported without reading additional files, especially workflow/compiler/planner types, kernel type definitions, snapshot internals beyond the inspected fragments, and any modules that may encode desired versus observed state explicitly.[cite:6][cite:16]
