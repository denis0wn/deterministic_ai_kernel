# Архитектурные инварианты (Execution Kernel Architecture)

В данном документе определены постоянные, нерушимые правила новой архитектуры ядра исполнения (`Execution Kernel Architecture`) для проекта `deterministic_ai_kernel`. Любые изменения в кодовой базе должны строго соответствовать этим инвариантам.

---

## 1. Изоляция Ядра (Kernel Isolation)

1.1. **Отсутствие доменных знаний:** Ядро исполнения (`Execution Kernel`) должно быть полностью свободно от доменных концепций автоматизации разработки (таких как `PatchCode`, `RunTests`, `AnalyzeTask`, `LocateBug`). Оно оперирует исключительно абстрактными понятиями: шаги спецификации, переходы состояний, идентификаторы ресурсов и хэши.
1.2. **Технологическая независимость:** Ядро не должно содержать прямых зависимостей от внешних технологий, протоколов или инструментов (таких как Git, файловая система, API языковых моделей, библиотеки MLX или MCP-серверы).
1.3. **Направление зависимостей:** Зависимости должны быть направлены от внешних слоев к внутренним. Ядро (`Execution Kernel`) зависит только от `Execution ABI` и `Execution Specification (ExecSpec)`. Слой провайдеров (`Providers Layer`) зависит от `Execution ABI` для реализации интерфейсов.

```
+--------------------+
|  Providers Layer   |
+---------+----------+
          | (реализует)
          v
+---------+----------+      +---------------------+
|   Execution ABI    | <--- |  Execution Kernel   |
+--------------------+      +----------+----------+
                                       | (интерпретирует)
                                       v
                            +----------+----------+
                            |       ExecSpec      |
                            +---------------------+
```

---

## 2. Неизменяемость и Декларативность (Immutability & Declarativeness)

2.1. **ExecSpec как единственный источник ограничений:** Все допустимые пути выполнения, требования к возможностям исполнителей (`capabilities`), политики безопасности и правила валидации артефактов должны быть описаны декларативно в `ExecSpec`. Запрещено хардкодить правила переходов и допусков внутри ядра.
2.2. **Неизменяемость спецификации:** Один раз созданная спецификация исполнения `ExecSpec` для конкретной задачи является неизменяемой (immutable) и идентифицируется своим криптографическим хэшем. Любое изменение в спецификации порождает новый `ExecSpec`.
2.3. **Принцип детерминизма переходов:** Применение одного и того же `ExecSpec` к одной и той же последовательности событий из `Canonical Event History` должно гарантированно приводить к идентичному состоянию ядра.

---

## 3. Событийная каноничность и Верификация (Evidence & Verification)

3.1. **Append-Only лог событий:** `Canonical Event History` (в составе `Evidence Layer`) является строго дополняемым и неизменяемым логом событий. Изменение или удаление записанных событий запрещено.
3.2. **Разделение записи событий и применения эффектов:** Ни один внешний эффект (запись файла, выполнение коммита, отправка запроса к LLM) не может быть выполнен без предварительного резервирования соответствующего намерения (`EFFECT_RESERVED`) в `Canonical Event History` и последующего подтверждения (`STEP_COMPLETED` / `STEP_FAILED`).
3.3. **Воспроизводимость состояния:** Слой реконструкции (`Reconstruction Layer`) обязан восстанавливать состояние выполнения исключительно на основе тройки параметров:
    $$\text{State} = \text{Reconstruct}(\text{ExecSpec}, \text{ExecutionABI}, \text{CanonicalEventHistory})$$
    Запрещено использовать любые побочные источники данных (например, системное время, состояние ФС или сетевой контекст) при реконструкции состояния.

---

## 4. Абстракция Выполнения (Execution Abstraction)

4.1. **Инверсия управления для выполнения шагов:** Выполнение физической работы по шагам делегируется зарегистрированным в ядре провайдерам (`Providers Layer`). Провайдеры общаются с ядром через строго определенный интерфейс вызова процедур (Execution ABI).
4.2. **Валидация артефактов по схеме:** Каждый артефакт, порожденный в процессе выполнения шага, должен проверяться на соответствие JSON-схеме, объявленной в `ExecSpec` для данного типа шага, перед записью в `Evidence Layer`.
4.3. **Версионирование ABI:** Любые изменения в структурах данных `Execution ABI` должны быть обратно совместимыми или изолированными с помощью версионирования для обеспечения возможности воспроизведения логов, записанных старыми версиями ядра.
