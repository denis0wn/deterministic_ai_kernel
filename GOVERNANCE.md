# DETERMINISTIC AI KERNEL — ARCHITECTURE CONSTITUTION v1

## 1. Миссия проекта

Deterministic AI Kernel — это универсальное детерминированное ядро исполнения AI-задач.

Это не AI-агент, не Workflow-система, не IDE, не Copilot.

Ядро является независимым Runtime, который способен выполнять любые AI Workflow через стабильные контракты.

Ядро не зависит от конкретной модели, конкретного Workflow или конкретной инфраструктуры.

## 2. Главная цель

Главная цель проекта — обеспечить детерминированное исполнение, а не детерминированную генерацию.

LLM может изменяться. Ответ модели может изменяться. Промпт может изменяться. Но процесс исполнения задачи должен быть воспроизводим.

## 3. Источник истины

Единственным источником истины является Event Log.

Не SQLite. Не Snapshot. Не Projection. Не Runtime State.

Все остальные структуры являются производными от Event Log. Replay всегда строится исключительно на основании Event Log.

## 4. Replay

Replay является главным механизмом воспроизводимости.

Replay восстанавливает выполнение. Replay не зависит от модели. Replay не использует Planner Cache. Replay читает историю событий и повторяет исполнение.

## 5. Planner

Planner больше не рассматривается как управляющий компонент.

LLM является исключительно генератором гипотез. Его задача — предложить ExecutionPlan. Никаких решений о состоянии Workflow он не принимает. Никаких изменений состояния системы он не производит.

## 6. Plan Generator

Plan Generator является внешним Provider.

Он получает Runtime Context. Возвращает ExecutionPlan. Не знает Event Store. Не знает Workflow. Не знает Executor. Не знает Runtime.

## 7. Workflow Engine

Workflow Engine является единственным владельцем жизненного цикла задачи.

Только Workflow Engine имеет право: создать Workflow, завершить Workflow, приостановить Workflow, возобновить Workflow, повторить Workflow, отменить Workflow.

Никакой другой модуль не имеет права менять Lifecycle.

## 8. Executor

Executor является максимально простым детерминированным исполнителем.

Executor: получает Step, исполняет Step, возвращает Result, фиксирует факт исполнения.

Executor не знает: Workflow, Planner, LLM, FSM, Business Logic. Executor никогда не принимает решений.

## 9. FSM

Конечный автомат полностью принадлежит Workflow Engine.

FSM является единственным местом хранения правил переходов состояний. Никакой другой модуль не имеет права менять состояние Workflow.

## 10. Event Store

Event Store представляет собой контракт хранения событий.

SQLite является только одной из возможных реализаций. Ядро не знает SQLite. Ядро знает только Event Store.

## 11. SQLite

SQLite не является архитектурной сущностью. SQLite относится исключительно к Infrastructure Layer.

Все вопросы WAL, PRAGMA, busy_timeout, checkpoint, cache_size являются вопросами реализации. Они не участвуют в архитектуре ядра.

## 12. Providers

Ядро работает исключительно через контракты. Ядро знает только интерфейсы. Никогда не знает реализации. Все внешние зависимости подключаются через Providers.

## 13. Capability Model

Все зависимости ядра выражаются через Capability.

Ядро знает возможность выполнить действие. Ядро не знает каким способом действие реализовано.

## 14. Ядро не знает реализации

Ядро никогда не знает: SQLite, PostgreSQL, Git, Filesystem, Cargo, Qwen, Gemma, Claude, OpenAI, MLX, Ollama, LM Studio.

Все это детали реализации.

## 15. Event ABI

Event ABI является стабильным контрактом. После получения статуса Frozen Event ABI не изменяется. Допускается только расширение.

## 16. Execution ABI

Execution ABI является стабильным контрактом между Kernel и Executor. После статуса Frozen обратно несовместимые изменения запрещены.

## 17. Workflow ABI

Workflow ABI отделяет ядро исполнения от конкретной Workflow-системы. Workflow может быть полностью заменен без изменения Kernel.

## 18. Public API

Public API никогда не изменяется без ADR. Любое изменение ABI требует новой версии.

## 19. Контракты

Каждый контракт проходит стадии: Draft → Accepted → Verified → Frozen → Deprecated.

Контракт считается стабильным только после появления автоматического интеграционного теста.

## 20. Ownership

Каждый слой имеет единственного владельца. Никакие обязанности не разделяются между несколькими модулями. Каждый инвариант имеет одного владельца.

## 21. Business Logic

В ядре отсутствует бизнес-логика.

Ядро ничего не знает о: CodeFix, AnalyzeTask, PatchCode, Research, Coding, Planning, Review. Любая предметная область находится выше Kernel.

## 22. Архитектурные зависимости

Зависимости направлены только внутрь. Внутренние слои никогда не знают внешние. Нарушение направления зависимостей запрещено.

## 23. Determinism

Запрещены любые скрытые источники недетерминизма. Любая операция, влияющая на Replay, должна быть воспроизводимой.

## 24. Runtime Context

Runtime Context Builder отвечает исключительно за построение контекста. Он не принимает решений. Он не изменяет Workflow. Он только подготавливает данные.

## 25. Validators

Любое решение Plan Generator проходит обязательную валидацию. Никакой результат модели не считается истинным до прохождения Validators.

## 26. Evolution

Архитектура развивается только через Governance. Не через случайные PR. Не через локальные решения. Не через изменения реализации.

## 27. Governance

Governance определяет правила изменения архитектуры. Specification определяет текущее устройство системы. Implementation определяет конкретную реализацию.

## 28. Архитектурный дрейф

Главным риском проекта считается архитектурный дрейф.

Любое изменение должно сохранять архитектурные инварианты. Автоматические проверки являются обязательной частью процесса разработки.

## 29. Приоритет развития

1. Governance
2. Specification
3. Architecture Tests
4. ABI
5. Refactoring
6. Infrastructure
7. Performance

Оптимизация никогда не выполняется раньше стабилизации архитектуры.

## 30. Главный принцип проекта

Deterministic AI Kernel строится вокруг детерминированного исполнения, стабильных контрактов и неизменяемой истории событий. Все модели, инфраструктура и внешние системы являются сменяемыми деталями реализации. Ядро существует независимо от них и развивается только через формализованные архитектурные правила.
